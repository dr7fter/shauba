# 01 · 向刷吧回传数据的格式

> 从 `AGENTS.md` 第七节拆出。只在**回传数据**时读这份。
> 铁律：只写 UTF-8 JSON 文件，**绝不直接写刷吧数据库、绝不改题库源文件**。

## 写入位置

未指定路径时写到 `%APPDATA%\com.shuaba.math\codex-inbox\{taskId}.json`。
后端约每 20 秒扫一次：成功 → 移入 `processed/`，失败 → 移入 `failed/`。

### ★ 必须原子写入（2026-09-04 实测踩坑）

后端每 20 秒扫一次，而 `json.dump` 是**逐段写**的——扫描撞上写入过程会读到半截
JSON，`serde_json::from_str` 直接失败，文件被 `rename` 进 `failed/`。

**正确做法：先写 `.tmp` 后缀，写完再 `os.replace` 成 `.json`。**
后端只扫 `.json`，rename 是原子的，永远不会读到半文件：

```python
tmp_path = path + '.tmp'
with open(tmp_path, 'w', encoding='utf-8') as f:
    json.dump(payload, f, ensure_ascii=False, indent=2)
os.replace(tmp_path, path)      # 原子，且 Windows 下可覆盖同名
```

**误判特征**：同一份文件先在 `failed/` 出现、稍后又出现在 `processed/`
（第二次扫描才成功）。看到这个现象，先查是不是写入没原子化，
而不是去改字段——字段没问题，是时序问题。

## 后端硬约束（违反会被拒收）

| 约束 | 值 |
|---|---|
| 单组题数 | ≤ 30 |
| `estimatedMinutes` | 5–240 |
| `questionRoles` 的 key | **必须是字符串题号**（`"155"`，不能是数字） |
| `taskId` 格式 | `SB-REC-YYYYMMDD-NNNN` / `SB-BATCH-...` / `SB-PLAN-...` |
| 题号 | **必须先在库里验证存在** |
| `coverage` | **`Vec<Value>` 对象数组**，不是字符串 |
| `noveltyPlan` | **`Vec<String>` 字符串数组**，不是字符串 |
| `successCriteria` | **`Vec<String>` 字符串数组**，不是字符串 |

⚠️ **这三个字段的类型坑（2026-09-04 实测踩过）**：早期文档把它们写成字符串，
按文档回传会直接在 `serde_json::from_str::<CodexPayload>` 处失败、文件被挪进 `failed/`
（注意：`insert_codex_payload` 失败**不会**挪文件，只打 warn——
**文件出现在 `failed/` = 反序列化失败，字段类型或结构不对**）。
以 `lib.rs` 的 `CodexPayload` 结构体为准。

验证题号存在：

```sql
SELECT id FROM questions WHERE id IN (155, 156);
```

无法验证就不要回传。

### 推送后的验证三连（必做）

1. `codex-inbox/` 根目录已清空（文件被扫走）
2. **以数据库为准，不看目录**：`processed/` 有文件才说明反序列化通过，
   但**真正落库才算数**（曾出现 `processed/` 与 `failed/` 同时存在同名文件的时序假象）

```sql
-- ① 是否入库、状态是否 pending（等待用户在 App 确认）
SELECT task_id, kind, status, created_at FROM codex_inbox
WHERE task_id LIKE 'SB-REC-20260904%' ORDER BY task_id;

-- ② 题组条数与顺序（position 从 0 开始，role 是否按预期）
SELECT i.position, i.question_id, i.role FROM recommendation_batch_items i
WHERE i.task_id = ? ORDER BY i.position;
```

3. `failed/` 里**没有本次 taskId**（有就是被拒了，按上面三个类型坑逐字段查）

⚠️ 表名与列名以 `PRAGMA table_info` 为准：`codex_inbox` 的状态列是 **`status`**
（不是 `state`），`recommendation_batches` **没有** `goal` / `estimated_minutes` 列
（`goal` 落在 `title`，其余只在 `payload_json` 里）。

## 1. 单题批改 `kind: "analysis"`

> 打分口径、六维独立性、断点写作纪律一律见 **`.agent/09-批改量规.md`（量规唯一副本）**。
> 本文件只讲字段与格式。

```json
{
  "schemaVersion": 1, "kind": "analysis", "taskId": "SB-YYYYMMDD-questionId-random",
  "questionId": 155,
  "summary": "简要诊断（含 $LaTeX$）",
  "verdict": "correct|partial|incorrect|uncertain",
  "earliestError": "最早错误步骤（含 $LaTeX$）或 null",
  "errorTags": ["概念盲区"], "secondaryTags": ["计算笔误"], "weaknessTags": ["幂零矩阵"],
  "advice": "一条可执行修复动作（含 $LaTeX$）",
  "betterSolution": "秒杀思路或 null",
  "stepScore": 72,
  "methodSoundness": null,
  "draftPaths": ["E:\\刷吧\\photo\\1.png"],
  "confidence": 0.95, "recommendedQuestionIds": [], "recommendationReason": null
}
```

`methodSoundness` 受控词表：`sound`（方法可复现）/ `lucky`（结果对但方法不可复现）/
`detour`（对但绕路）。**只在 `verdict: "correct"` 时填 `lucky`/`detour`，其余一律 `null`**；
词表外的值后端直接丢弃（`normalize_method_soundness`），填错等于没填。

`errorTags` **只放 1 个主标签**（取最早断点所属类），其余病因进 `secondaryTags`。
病因归一只看主标签，多标签会让概念盲区被判成瞄准失误，而聚类直接决定明天推什么题。

`stepScore`：`partial` / `incorrect` 必填有效步骤分（0–100 整数），
`correct` / `uncertain` 填 `null`。报告会显示它——学员要看得见"自己错得多可惜"。

`ratingTier` 与 `difficultyMultiplier` **不再需要回传**：档位由前端按分数自算，
难度系数由内核从 `questions.difficulty` 派生（被评分者自选系数 = 评分可被自己放大）。

## 2. 整组批改 `kind: "batch"`

草稿张数少于题目数时，**只批改上传了草稿的题**，未收到草稿的题不出现在 `batchAttempts` 中。

```json
{
  "schemaVersion": 1, "kind": "batch", "taskId": "SB-BATCH-YYYYMMDD-random",
  "summary": "整组摘要（含 $LaTeX$）", "errorTags": ["方法未掌握"],
  "weaknessTags": ["定积分对称性与King变换"], "confidence": 0.95,
  "recommendedQuestionIds": [],
  "batchAttempts": [
    { "questionId": 155, "result": "correct|wrong|uncertain", "selfRating": 2,
      "durationSeconds": 120, "summary": "（含 $LaTeX$）",
      "verdict": "correct|partial|incorrect|uncertain",
      "earliestError": "…或 null", "errorTags": ["战术绕路"], "secondaryTags": [],
      "weaknessTags": ["待定系数法"], "advice": "（含 $LaTeX$）",
      "betterSolution": "…或 null", "stepScore": 68, "methodSoundness": null,
      "draftPaths": ["E:\\刷吧\\photo\\3.png"],
      "diagnosis": { "…见第 5 节…" }, "confidence": 0.95 }
  ]
}
```

- `result` 只能 `correct` / `wrong` / `uncertain`
- `selfRating` 1–4
- `uncertain` 不写作答记录，仅留诊断

## 3. 推荐题目 `kind: "recommendation"`

⚠️ **推荐题必须用完整字段**（后端 `lib.rs` payload 结构体解析
`question_roles` / `recommendation_order` / `estimated_minutes`，缺了角色会默认 `consolidate`）。
推荐行为约束（candidates-only、角色语义、新颖度分级）见根目录 `AI_LEARNING_POLICY.md`，两份配合使用。

```json
{
  "schemaVersion": 2, "kind": "recommendation", "taskId": "SB-REC-YYYYMMDD-random",
  "questionId": null, "summary": "本次荐题策略", "verdict": null, "earliestError": null,
  "errorTags": [], "weaknessTags": ["薄弱知识"], "advice": null, "betterSolution": null,
  "confidence": 0.9,
  "recommendedQuestionIds": [155, 156, 157],
  "recommendationOrder": [157, 155, 156],
  "questionRoles": { "155": "diagnosis", "156": "consolidate", "157": "review" },
  "estimatedMinutes": 45,
  "goal": "批次标题（简短，显示在收件箱卡片上；不填则用 summary 前若干字）",
  "coverage": [
    { "label": "覆盖目标一句话", "questionIds": [155, 156] },
    { "label": "另一个覆盖目标", "questionIds": [157] }
  ],
  "noveltyPlan": ["基础阶段每题只改一个因素", "迁移题才允许换入口"],
  "successCriteria": ["动笔 30 秒内写出关键识别动作", "正确率 ≥ 60% 视为通过"],
  "recommendationReason": "推荐理由（引用历史证据）",
  "sourceEvidenceIds": []
}
```

- `questionRoles` 的 key **必须是字符串题号**；值只能用
  `diagnosis` / `method_choice` / `consolidate` / `integration` / `transfer` / `timed` / `challenge` / `review`
- `recommendationOrder` 是作答顺序（数组），空则按 `recommendedQuestionIds` 原序
- 落库后顺序在 `recommendation_batch_items.position`、角色在 `.role`（**没有** `recommendation_order` 列）
- `coverage` 元素里的 `questionIds` 会被逐一校验**必须属于本题组**，引用了题外题号则整份拒收
  （`lib.rs` 约 1734 行）；`label` 等其余键是 `Value`，自由携带

## 4. 每日作战计划 `kind: "daily_plan"`

支持提前一天制定明日或指定日期的基础与进阶清单。

```json
{
  "schemaVersion": 1, "kind": "daily_plan", "taskId": "SB-PLAN-YYYYMMDD-random",
  "planDate": "2026-09-01",
  "summary": "明日攻坚：定积分 King 变换与多元极值高光突破",
  "baseQuests": [
    { "id": "b1", "title": "攻克 3 道定积分真题基础题", "targetType": "count",
      "targetCount": 3, "categoryPath": "高等数学/一元函数积分学", "questionIds": [] },
    { "id": "b2", "title": "复习第 5 讲张宇基础讲义笔记", "targetType": "manual", "questionIds": [] }
  ],
  "advancedQuests": [
    { "id": "a1", "title": "攻克 1 道真题多元极值压轴（Rating ≥ 1.35）",
      "targetType": "rating_challenge", "minRating": 1.35, "questionIds": [] }
  ]
}
```

用户在收件箱一键确认后，落入对应日期的每日清单。

## 5. 断点诊断块 `diagnosis`（2026-09-03 新增）

`analysis` 与 `batch` 两种批改**每题必填**（挂在题级，与 `verdict` 同级）。
报告按「我的入口 → 断点 → 为什么是死路 → 识别规则 → 正确入口」的认知动线渲染，
字段缺一项，动线就断一环。

```json
"diagnosis": {
  "errorCode": "E-027",
  "title": "根式换元入口缺失",
  "severity": "L1",
  "myEntry": "学员落笔时的第一个动作（含 $LaTeX$）",
  "whyDeadEnd": "这条路径为什么走不通（讲原理，不讲步骤，含 $LaTeX$）",
  "rule": { "negation": "看到什么特征时禁止做什么", "positive": "该做什么" },
  "fork": { "step": 1, "label": "换元选择",
            "myPath": "学员实际走的路径（含 $LaTeX$）",
            "standardPath": "正确路径（含 $LaTeX$）",
            "consequence": "走错之后的后果" },
  "acceptance": "一条可判定的验收判据",
  "nextAction": "明天就能做的一条动作",
  "whyItWorked": null
}
```

| 字段 | 必填 | 说明 |
|---|---|---|
| `errorCode` | 是 | `characteristic.md` 里已有编号就回填（如 `E-027`）；尚未编码填 `null`。**同一入口导致的题必须填同一个 code**，复发统计全靠它 |
| `title` | 是（错题） | 断点名，一句话，不复述题干 |
| `severity` | 是（错题） | `L1` 致命 / `L2` 战术 / `L3` 精度 |
| `myEntry` | 是 | 学员当时的第一个动作，原话式一句 |
| `whyDeadEnd` | 是（错题） | 讲**原理**为什么走不通，不写步骤流水账 |
| `rule.negation` | 是（错题） | 否定式在前：「看到 X 禁止做 Y」 |
| `rule.positive` | 是 | 该做什么 |
| `fork.*` | 是（错题） | 路径分叉对照（我的路径 vs 标准路径），`step` 是分叉发生在第几步 |
| `acceptance` | 是（错题） | 可判定的验收判据，要能当场判真假 |
| `nextAction` | 是（错题） | 明天就能做的一条动作 |
| `whyItWorked` | 是（correct） | 这条入口为什么在这道题上成立（讲结构，不讲步骤） |

三条硬规矩：

1. **`verdict` 为 `correct` 的题填「三字段固化卡」**：`myEntry` + `rule.positive` + `whyItWorked`，
   其余字段填 `null`。做对的题同样要留证据——画像封盘（连续 2 次独立避坑 → 🟢 已固化）
   靠的就是它。**不要填空对象，也不要整块 null**
2. **严禁复述题干**。`myEntry` 写学员做了什么，不是题目问了什么
3. `errorCode` 只在画像里真有编号时才填；**不造号**，宁可 `null`——
   未编码的断点在报告里显示为「未编码」并给出待补提示，属于正常状态

### 两条工程约束（不遵守等于白写）

1. **未在后端结构体里声明的字段会在入库时被丢掉。**
   `scan_inbox` 存进 `payload_json` 的是反序列化后**重新序列化**的 `CodexPayload`，
   结构体没写的字段直接消失（`diagnosis` 就因为这个，从 2026-09-03 接入报告
   （commit `ceb4423`）到 2026-09-04 补上字段之间从未真正入库，
   报告六段动线全部退化成降级派生）。新增回传字段必须同步改
   `lib.rs` 的 `CodexPayload` / `BatchAttempt`，并加一条留存回归测试。
2. **`result` 由 `verdict` 派生，不是独立判断**：
   `correct→correct`、`partial→wrong`、`incorrect→wrong`、`uncertain→uncertain`。
   两个字段都要输出（历史兼容），但内容必须满足该映射，否则整份回传会被拒收。

### 落库与读取路径

后端 `lib.rs` 用 `json_extract(payload_json, '$.diagnosis.errorCode')` 从
`codex_inbox` 的历史 payload 里取 `verdict / earliestError / errorCode`，
供「断点档案 · 修复时间线」展示（`AttemptHistoryEntry`）。
`get_error_code_history` 进一步按 `questionId + errorCode` 取出**历次命中的
`diagnosis.rule.negation / acceptance / nextAction / stepScore`**，
让报告能把两次批改并排显示。所以 `diagnosis.errorCode` 一旦回传即可被时间线检索到，
**改字段名需同步改这两处 SQL**。

## 回传后的验证三连（必做）

1. `codex-inbox/failed/` 为空
2. JSON 文件已进入 `codex-inbox/processed/`
3. 题组落库条数与顺序正确：

```sql
SELECT i.position, i.question_id, i.role, q.category_path
FROM recommendation_batch_items i
LEFT JOIN questions q ON q.id = i.question_id
WHERE i.task_id = ? ORDER BY i.position;
```

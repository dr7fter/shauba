## 2. v0.9.1 产品目标

### 2.1 一句话目标

> 任何一次压力模拟或 Codex 批改，都必须能够从“开始”追踪到“确认”，并且只把有可靠证据的结果写入正式作答、SRS 和进展统计。

### 2.2 版本范围

#### 本版本必须完成

1. 修复 batch Codex 回传的真实耗时没有写入作答记录的问题。
2. 统一压力模拟、Codex 任务、inbox、attempts、progress 之间的状态关系。
3. 明确并实现 `uncertain` 的数据规则：保留诊断，但不写入正式作答与掌握度。
4. 对 batch 确认增加幂等保护，重复确认不能重复生成作答记录。
5. 压力模拟完成后可以恢复、查看、确认，并最终得到明确的 `graded` 或 `abandoned` 状态。
6. 补充“压力模拟 → Codex 回传 → inbox 确认 → 正式作答”的集成测试。
7. 保证旧数据库、旧 inbox JSON、题库源文件不被破坏。

#### 本版本暂不做

- 云同步
- 社交、排行榜、游戏中心扩展
- 新的奖励/经验系统
- 屏幕输入式主观题作答
- 大规模 UI 视觉重构
- 全量前端/Rust 模块拆分

### 2.3 建议纳入但需用户确认

## 3. 当前已确认的技术问题

### 3.1 batch 批改耗时被固定为 30 秒

`src-tauri/src/lib.rs` 的 `apply_batch_payload` 当前把 `BatchAttempt.durationSeconds` 忽略，使用固定 `30` 写入 `attempts.duration_seconds`。

影响：今日用时、平均速度、节奏分析和后续诊断可能失真。

修复方向：

```text
优先使用 batchAttempt.durationSeconds
否则使用对应 pressure_answers.duration
最后才使用安全兜底值
统一 clamp 到 1..1800 秒
```

### 3.2 压力会话与 inbox 确认缺少完整闭环

压力会话位于 supplemental 数据库，Codex inbox 和 attempts 位于主数据库。当前已经存在 `task_id` 关联字段和 `attach_pressure_task`，但确认 batch 后需要进一步保证：

```text
awaiting_codex → 用户确认 → graded
```

并保存可追踪的：

- session_id
- task_id
- confirmed_at
- 实际写入的 question_id 集合
- uncertain / 未上传题目集合

### 3.3 `gradingReport` 前端路径未完全接通

当前存在 `gradingReport` 状态和压力报告 UI，但正常 inbox 确认路径没有稳定地将批改结果注入该状态。需要在本版本中做明确取舍：统一到 inbox，或把报告真正接通。

### 3.4 现有测试缺少跨数据库、跨命令流程验证

已有单元测试覆盖证据模型、SRS、批次、压力会话部分行为，但仍需要补充真实流程级测试：

```text
create_pressure_session
→ submit_pressure_answer × N
→ complete_pressure_session
→ create_codex_batch_task
→ 写入 batch JSON
→ confirm_inbox
→ 检查 attempts / progress / pressure_sessions
```

## 4. v0.9.1 数据规则

### 4.1 结果类型

正式作答结果只能是：

- `correct`
- `partial`
- `wrong`
- `uncertain`

其中：

- `correct`、`partial`、`wrong` 可以进入正式作答记录。
- `uncertain` 保留诊断和原始 inbox，但不进入掌握度、正确率和 SRS 推进。

### 4.2 耗时规则

所有进入 `attempts` 的耗时必须：

```text
1 <= durationSeconds <= 1800
```

优先级：

1. Codex 返回的 `durationSeconds`
2. 压力会话逐题保存的 duration
3. 当前前端作答计时
4. 最终安全兜底值

### 4.3 幂等规则

同一 `taskId + questionId + diagnosisId` 的批改结果重复确认时，不得重复插入正式作答。

重复扫描同一个 inbox JSON 时，不得产生第二条 inbox 记录。

### 4.4 部分批改规则

Codex 只批改实际收到草稿的题目。未收到草稿的题目不写入 `batchAttempts`，也不生成“未作答”占位记录。

## 7. 已确认的报告页方向

### 7.1 产品定位

```text
Codex 限制指令 + 草稿 + 逐题耗时 + 既有正确/熟练级别
                         ↓
                    Codex 批改结果
                         ↓
                   Inbox 预览与确认
                         ↓
            gradingReport / pressure_reports
              （独立的学习情况展示页）
```

- Inbox 是工作流入口：确认前允许查看、确认或驳回。
- 报告页是学习复盘入口：展示已确认的本次学习情况，不承担再次确认。
- `attempts`、`progress` 仍是正式学习统计来源；报告是基于确认结果的可回看快照。
- Codex 可以补充诊断、错误步骤、更好解法和建议，但不能擅自改变用户已有的正确性/熟练度规则。

### 7.2 报告页第一版内容

1. 本次概览：题数、已批改题数、正确/部分正确/错误/不确定数量、总时长、平均用时。
2. 学习表现：正确率、熟练度分布、速度与稳定性提示。
3. 逐题报告卡：题目、结论、实际耗时、熟练度、最早错误、错误标签、薄弱知识点。
4. 方法复盘：Codex 给出的更好解法、易错边界和可执行建议。
5. 后续行动：建议复习的知识点和推荐题目；推荐题目必须经过真实题库 ID 校验。
6. 数据说明：明确显示未上传草稿的题不参与批改；`uncertain` 只保留诊断，不进入正式作答与掌握度统计。

### 7.4 用户已确认的压力功能规则

- 压力模拟计时按真实经过时间计算；切换窗口、最小化或关闭 App 后，重新打开时继续计时。
- 其它 Phase A 推荐方案全部采用：中途可恢复、明确放弃才 abandoned、允许部分批改、耗时按证据优先级回退、旧异常会话保留并妥善标记、先源码验收后打包、只做必要的前端拆分。

### 7.3 生成时机

默认在 Inbox 确认成功后生成并保存报告快照；用户再次打开报告页时直接读取已保存报告，不重复调用 Codex。若后续确需重新分析，应作为明确的“重新生成报告”操作，不能静默覆盖原报告。

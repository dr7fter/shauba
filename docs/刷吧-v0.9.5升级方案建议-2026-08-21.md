# 刷吧 v0.9.5 升级方案建议

**创建日期**：2026-08-21  
**当前版本**：v0.9.4  
**目标版本**：v0.9.5  
**方案性质**：战略规划建议，非立即实施

---

## 1. 当前状态评估

### 1.1 v0.9.4 核心能力盘点

基于代码审查，当前版本已具备：

**核心刷题流程**
- 纸笔优先作答（选择题自动判定 + 主观题自评）
- outcome（正确性）与 fluency（熟练度）分离评估
- 实时计时与节奏评估
- Codex 单题/整组草稿批改
- 压力模拟模式（真实考试环境 + 逐题计时 + Codex 批改）

**智能推荐与复习**
- AI 推荐题组（基于薄弱点、到期复习、难度匹配）
- SRS 间隔复习系统
- 自定义队列管理
- 变式题攻坚
- 昨日错题重测

**数据可视化与进展**
- 每日趋势曲线
- 掌握度地图
- 薄弱雷达图
- 复盘历史记录
- 连续刷题天数统计

**数据管理**
- SQLite 本地存储（主库 + 补充库）
- 数据库备份与恢复
- 题库分页浏览与搜索
- 笔记与收藏功能

### 1.2 v0.9.1 → v0.9.4 演进重点

根据文档记录，最近几个版本重点完成：

- **v0.9.1**：压力模拟数据闭环、真实耗时写入、幂等保护、uncertain 规则、独立学习报告页
- **v0.9.2 - v0.9.4**：迭代修复与稳定性增强

### 1.3 技术栈现状

- **前端**：React 19.2.8 + TypeScript 6.0.2 + Vite 8.2.0 + Framer Motion 13.1.0
- **后端**：Tauri 2.11.3 + Rust 1.77.2
- **核心文件规模**：
  - `src/App.tsx`：4339 行
  - `src/App.css`：2263 行
  - `src-tauri/src/lib.rs`：5880 行
  - `src/api.ts`：370 行

### 1.4 当前痛点识别

**架构层面**
- 单体组件过大（App.tsx 4339 行），维护成本高
- 样式文件膨胀（App.css 2263 行），缺少模块化隔离
- Rust 后端单文件实现（lib.rs 5880 行），缺少清晰分层

**功能层面**
- 压力模拟与正常刷题模式切换体验可优化
- 学习报告页展示深度可增强
- 题目搜索与筛选能力较基础
- 数据导出能力有限（仅支持 CSV）

**性能层面**
- 大量题目渲染性能未做虚拟化
- 图片资源加载未做优化
- 状态管理较为分散

## 2. v0.9.5 升级方案建议

### 2.1 方案 A：稳健演进（推荐）

**核心定位**：在现有架构基础上做渐进式优化，专注用户体验提升与关键功能增强。

#### 前端优化方向

**1. 组件拆分与模块化（高优先级）**
```
src/App.tsx (4339行) 拆分为：
  ├─ src/views/
  │   ├─ TodayView.tsx          （今日刷题主视图）
  │   ├─ LibraryView.tsx         （题库浏览）
  │   ├─ ReviewView.tsx          （复盘）
  │   ├─ MasteryView.tsx         （掌握度地图）
  │   └─ InsightsView.tsx        （进展数据）
  ├─ src/components/
  │   ├─ QuestionCard.tsx        （题目卡片）
  │   ├─ AnswerPanel.tsx         （作答面板）
  │   ├─ PressureModeFlow.tsx    （压力模拟完整流程）
  │   ├─ GradingReportModal.tsx  （学习报告）
  │   └─ QueuePanel.tsx          （队列管理）
  └─ src/hooks/
      ├─ useTimer.ts             （计时逻辑复用）
      ├─ usePracticeSession.ts   （会话状态管理）
      └─ useKeyboard.ts          （快捷键）
```

**预期收益**：
- 单文件代码量降至 300-500 行
- 逻辑职责清晰，便于维护与测试
- 多人协作时减少冲突

**2. 样式系统重构（中优先级）**
```
src/App.css (2263行) 重构为：
  ├─ src/styles/
  │   ├─ tokens.css              （设计令牌）
  │   ├─ base.css                （基础样式）
  │   ├─ components/
  │   │   ├─ button.module.css
  │   │   ├─ card.module.css
  │   │   └─ modal.module.css
  │   └─ views/
  │       ├─ today.module.css
  │       └─ library.module.css
```

采用 CSS Modules 实现样式作用域隔离。

**3. 压力模拟体验增强（高优先级）**
- 增加"暂停"功能（真实经过时间仍计时，但允许短暂休息）
- 压力模拟历史记录页（查看所有历史会话与成绩趋势）
- 未完成会话恢复入口优化（当前需要从状态恢复）
- 批改报告增加逐题耗时对比图（实际用时 vs 基准用时）

**4. 学习报告深度增强（中优先级）**
- 错误类型统计饼图（概念边界、策略选择、推导计算等）
- 知识点掌握度雷达图（基于 weaknessTags 聚合）
- 历史报告对比（本次 vs 上次在相同知识点的表现）
- 报告导出为 PDF（便于打印复习）

**5. 题库搜索与筛选增强（中优先级）**
- 按知识点标签筛选（当前仅支持章节分页）
- 按难度区间筛选
- 按作答历史筛选（未做过、做错过、收藏）
- 搜索结果高亮显示

#### 后端优化方向

**1. Rust 代码模块化（高优先级）**
```
src-tauri/src/lib.rs (5880行) 拆分为：
  ├─ src-tauri/src/
  │   ├─ lib.rs                  （入口与命令注册）
  │   ├─ database/
  │   │   ├─ mod.rs
  │   │   ├─ main_db.rs          （主数据库操作）
  │   │   └─ supplemental_db.rs  （补充数据库）
  │   ├─ models/
  │   │   ├─ attempt.rs
  │   │   ├─ pressure.rs
  │   │   └─ question.rs
  │   ├─ services/
  │   │   ├─ practice.rs         （刷题业务逻辑）
  │   │   ├─ review.rs           （复习逻辑）
  │   │   └─ recommendation.rs   （推荐算法）
  │   └─ utils/
  │       ├─ srs.rs              （SRS 算法）
  │       └─ evidence.rs         （证据模型）
```

**2. 数据库性能优化（中优先级）**
- 为高频查询添加复合索引
- 实现查询结果缓存（特别是进展统计）
- 优化 attempts 表的聚合查询（使用物化视图或定期汇总表）

**3. API 层优化（中优先级）**
- 统一错误处理机制（当前错误信息较分散）
- 增加请求日志记录（便于排查问题）
- 关键操作增加事务保护（如批量确认 inbox）

#### 新功能建议

**1. 快捷键系统（高优先级）**
- 刷题时：数字键 1-4 选择选项、Space 下一题、Backspace 撤销
- 全局：Ctrl+N 新建自定义队列、Ctrl+R 刷新推荐、Ctrl+P 进入压力模拟

**2. 数据导出增强（中优先级）**
- 导出学习报告为 PDF
- 导出错题本（含题目、草稿、批改结果）
- 导出进展数据为 Excel（便于自行分析）

**3. 主题切换（低优先级）**
- 浅色模式 / 深色模式切换
- 当前为固定深色主题

**4. 离线 AI 批改探索（低优先级）**
- 集成本地小模型（如 Phi-3）做选择题自动判定
- 减少对外部 Codex 的依赖

#### 实施建议

**Phase 1（2-3 周）：组件拆分与模块化**
- 拆分 App.tsx 为独立视图组件
- 拆分 lib.rs 为清晰模块
- 保持功能零变化，纯重构

**Phase 2（1-2 周）：压力模拟增强**
- 历史记录页
- 暂停功能
- 批改报告可视化增强

**Phase 3（1-2 周）：样式系统与快捷键**
- CSS Modules 迁移
- 快捷键系统实现
- 主题切换基础设施

**Phase 4（1 周）：测试与打磨**
- 回归测试
- 性能测试
- 文档更新

**预计总工期**：5-8 周

---

### 2.2 方案 B：激进重构（不推荐）

**核心定位**：大规模技术栈升级与架构重写。

#### 主要变更

**前端**
- 引入状态管理库（Zustand / Jotai）
- 使用 TanStack Query 管理服务端状态
- 引入 React Router 做视图路由
- 样式迁移到 Tailwind CSS
- 组件库迁移到 Radix UI

**后端**
- Rust 后端完全分层重写
- 引入 async runtime（tokio）
- 数据库访问层使用 SeaORM
- 增加 WebSocket 支持（实时同步）

**新功能**
- 云同步（需要后端服务）
- 多设备数据同步
- 社交功能（成绩分享、排行榜）

#### 风险评估

**极高风险**
- 开发周期：3-6 个月
- 引入大量新依赖，学习成本高
- 现有功能迁移工作量巨大
- 用户数据迁移风险
- 稳定性倒退风险

**不推荐理由**
- 当前架构虽然单体，但功能完整且稳定
- 用户核心需求已被满足，激进重构收益不明显
- 技术债务可通过渐进式重构解决
- 云同步等功能需要额外的服务端开发与运维成本

export function useKeyboard(config: KeyboardConfig) {
  useEffect(() => {
    const handler = (e: KeyboardEvent) => {
      if (e.ctrlKey && e.key === 'n') {
        e.preventDefault()
        config.onNewQueue?.()
      }
      if (e.key === ' ' && config.onNext) {
        e.preventDefault()
        config.onNext()
      }
      // ... 其他快捷键
    }
    window.addEventListener('keydown', handler)
    return () => window.removeEventListener('keydown', handler)
  }, [config])
}

## 5. 风险评估与缓解

### 5.1 技术风险

| 风险项 | 影响 | 概率 | 缓解措施 |
|--------|------|------|----------|
| 组件拆分引入 bug | 中 | 中 | 完整回归测试；分阶段拆分；保留旧代码分支 |
| Rust 模块化编译失败 | 高 | 低 | 逐模块迁移；保持 API 契约不变 |
| 性能倒退 | 中 | 低 | 性能基准测试；关键路径性能监控 |
| 用户数据损坏 | 高 | 极低 | 数据库备份；只读操作优先；充分测试 |

### 5.2 进度风险

| 风险项 | 影响 | 概率 | 缓解措施 |
|--------|------|------|----------|
| 开发周期超预期 | 中 | 中 | 核心功能优先；非核心功能降级为可选 |
| 测试覆盖不足 | 高 | 中 | 自动化测试先行；关键路径人工测试 |
| 文档更新滞后 | 低 | 高 | 代码重构时同步更新文档 |

### 5.3 用户体验风险

| 风险项 | 影响 | 概率 | 缓解措施 |
|--------|------|------|----------|
| 操作习惯改变 | 中 | 低 | 保持交互一致性；快捷键作为增强而非替代 |
| 新功能学习成本 | 低 | 中 | 功能引导；渐进式揭示 |
| 稳定性下降 | 高 | 低 | 充分测试；灰度发布（先内部使用） |

## 8. 决策建议

### 推荐方案：**方案 A（稳健演进）**

**理由**：
1. **风险可控**：渐进式重构，不影响现有功能稳定性
2. **收益明显**：代码可维护性大幅提升，为后续开发打好基础
3. **周期合理**：5-8 周可完成，不会长期阻塞其他需求
4. **用户价值**：压力模拟增强、学习报告深化、快捷键等直接提升使用体验

### 不推荐方案：**方案 B（激进重构）**

**理由**：
1. **风险过高**：大规模重写，稳定性难以保证
2. **周期过长**：3-6 个月，机会成本高
3. **收益不确定**：技术栈升级本身不直接产生用户价值
4. **维护负担**：新依赖引入后的长期维护成本

# 三、必须先理解的核心判断

## 1. 坚果云只能实现近实时，不能实现严格实时

当前同步通道是坚果云 WebDAV，不是 WebSocket 或实时服务器。

因此本次不得宣传为：

```text
实时在线
```

实际应定义为：

```text
近实时状态
```

推荐状态延迟目标：

```text
好友页打开且双方 App 正常运行时：约 1～2 分钟内更新
```

如果出现以下情况，允许延迟：

- 坚果云网络延迟；
- WebDAV 409；
- App 在后台；
- 电脑休眠；
- 对方关闭 App；
- 云端同步失败。

UI 必须明确显示：

```text
最近心跳时间
```

不能只显示一个永远不变的“在线”。

---

## 2. 好友页面必须读取“公开数据投影”，不能读取好友数据库

好友的数据页不能复用当前用户的：

```text
E:\刷吧\src\views\InsightsView.tsx
```

因为 `InsightsView` 读取的是本机 SQLite 数据。

好友页面必须读取：

```text
本地缓存的好友公开快照
```

好友公开快照由对方本机生成，然后上传到坚果云。

好友之间不能互相读取数据库。

---

## 3. 学习报告必须脱敏后同步

不得直接上传当前本机的完整 `GradingReport`。

好友公开报告必须是一个新的公开 DTO，只包含用户允许被好友看到的内容。

# 四、P0：虚空好友治理

这是最高优先级，必须先完成并测试，之后再做新的好友数据页。

## 4.1 严格好友白名单

当前远端扫描逻辑会扫描共享目录中所有：

```text
shuaba-friend-*.json
```

必须改变为：

```text
只有用户主动添加过的好友码，才能进入正常好友导入流程
```

新增或调整逻辑：

```text
requestedCodes = getSavedFriendCodes()
knownProfileIds = 已知好友的 profileId 集合
blockedIdentities = 已屏蔽身份集合
```

远端文件处理规则：

### 情况 A：文件好友码在 `requestedCodes`

允许正常解析和更新。

### 情况 B：文件好友码不在 `requestedCodes`，但文件中的 `profileId` 是已知好友

允许作为“好友改码”候选处理：

- 不新增陌生好友；
- 更新该好友的当前好友码；
- 将旧好友码加入历史别名；
- 清理旧同步状态；
- 保证最终仍然只有一个好友记录。

### 情况 C：好友码和 profileId 都不是已知身份

不得导入。

只能统计：

```text
unrecognizedFiles
```

并提示：

```text
共享目录中发现 X 个未添加好友文件，已忽略
```

不得写入：

```text
shuaba_friends_roster_v2
shuaba_friend_codes_v2
shuaba_friend_sync_state_v1
```

不得生成 `FriendProfile`。

## 4.2 屏蔽身份机制

新增本地存储：

```text
shuaba_friend_blocked_identities_v1
```

建议结构：

```ts
type BlockedFriendIdentity = {
  profileId?: string
  friendCodes: string[]
  blockedAt: string
  reason?: string
}
```

删除好友时：

1. 删除当前好友资料；
2. 删除当前好友码；
3. 删除该好友所有历史好友码；
4. 删除同一 `profileId` 的同步状态；
5. 写入 blocked identity；
6. 后续同步禁止恢复此身份。

注意：

```text
不得自动删除坚果云中的远端文件
```

只做本地屏蔽。

## 4.3 虚空好友迁移处理

首次运行新逻辑时，不得静默删除已有数据。

需要执行一次本地好友数据整理：

1. 读取 roster；
2. 读取 friend codes；
3. 读取 sync states；
4. 规范化好友码；
5. 根据 friendCode 和 profileId 去重；
6. 找出不在有效好友白名单中的记录；
7. 将可疑记录标记为：

   ```text
   unconfirmed
   ```

8. 在好友页或同步设置中提供：

   ```text
   保留
   归档
   删除并屏蔽
   ```

不要让用户必须打开浏览器开发工具或手动删除 localStorage。

## 4.4 去重必须处理身份传递关系

当前简单的 `findIndex` 去重不够可靠。

需要保证以下情况最终只保留一个好友：

```text
A: code = CODE-A, profileId = P1
B: code = CODE-A, profileId = P2
C: code = CODE-C, profileId = P2
```

A、B、C 应根据关联关系合并成一组。

可以使用：

- 并查集；
- 身份连通分量；
- 或等价的多轮合并算法。

每组保留记录时，优先级：

1. 非 legacy profileId；
2. 最近成功同步时间最新；
3. 最近公开快照时间最新；
4. 数据字段最完整；
5. 最后才使用数组顺序。

# 八、P1：近实时状态实现

## 8.1 状态计算规则

不能把快照里的静态 `status: online` 直接当作当前在线状态。

根据 `heartbeatAt` 计算：

```text
心跳 <= 90 秒：
  有 currentMatchId → 正在刷题
  无 currentMatchId → 在线

90 秒 < 心跳 <= 5 分钟：
  刚刚活跃/空闲

超过 5 分钟：
  离线

公开资料超过 7 天没有成功更新：
  数据过期
```

如果从未成功同步：

```text
状态未知
```

## 8.2 上传频率

推荐：

```text
App 启动：发布一次
App 回到前台：发布一次
正在刷题：约每 60 秒发布一次
完成题组：立即发布一次
App 退出：尽量发布一次
```

不要在后台无限高频上传。

## 8.3 拉取频率

保持当前低负载策略：

```text
好友页打开时立即同步
好友页可见时每 60 秒同步一次
页面不可见时暂停自动同步
提供手动刷新
```

同步过程必须异步进行，先显示本地缓存。

# 九、P1：坚果云同步和 409 处理

每个用户只能写自己的公开文件：

```text
用户 A 写 A 的文件
用户 B 写 B 的文件
```

好友只拉取，不写好友文件。

遇到：

```text
HTTP 409 Conflict
```

处理要求：

1. 标记为可重试错误；
2. 自动退避重试；
3. 不删除远端文件；
4. 不覆盖本地最近一次有效快照；
5. 不把好友状态直接改成离线；
6. 不阻塞好友页；
7. 不阻塞完成题组；
8. 将错误显示为：

   ```text
   本次公开数据上传失败，稍后自动重试
   ```

同步协议必须有：

```text
revision
snapshotId
exportedAt
snapshotHash
```

同一个 `profileId`：

- 只接受更高 revision；
- 相同 revision + 相同 hash 视为 unchanged；
- 相同 revision + 不同 hash 视为冲突，不要覆盖本地有效数据。

# 十二、好友配置体验

目标是：

```text
好友首次配置一次，之后自动同步
```

建议新增“好友同步邀请”流程：

你这边：

```text
创建邀请
→ 生成邀请文件或邀请码
→ 指定共享目录
→ 分享坚果云文件夹
```

好友这边：

```text
导入邀请
→ 自动填充端点、共享目录和你的好友码
→ 首次填写自己的坚果云应用密码
→ 完成
```

邀请文件可以包含：

```text
endpoint
folder
friendCode
profileId
协议版本
```

不能包含：

```text
你的坚果云主密码
你的 appPassword
```

不能把配置写入好友快照。

如果用户坚持让朋友使用同一个坚果云账号，可以兼容，但必须在 UI 中明确风险：

```text
共用账号会让对方拥有该账号可访问范围内的文件权限，不建议用于正式使用。
```

# 十五、必须验证的测试场景

## 场景 1：陌生云端文件

共享目录放入一个没有主动添加过的合法好友文件。

预期：

```text
不会进入好友列表
不会写入好友 roster
不会写入好友码列表
只显示未识别文件数量
```

## 场景 2：删除好友后同步

删除好友后再次同步。

预期：

```text
好友不会因为旧云端文件重新出现
```

## 场景 3：好友改码

好友从旧好友码改成新好友码，但 `profileId` 不变。

预期：

```text
仍然只显示一个好友
历史好友码被记录为别名
不会出现两个好友
```

## 场景 4：重复快照

重复拉取同一个快照。

预期：

```text
不重复生成好友
不重复生成动态
不重复生成比赛
```

## 场景 5：远端暂时缺失

好友文件一次拉取不到。

预期：

```text
保留上次数据
显示暂未同步
不立即删除好友
不伪装成正常在线
```

连续多次失败后：

```text
显示数据过期
可以归档
```

## 场景 6：409 Conflict

上传收到 HTTP 409。

预期：

```text
本地刷题不受影响
界面不卡顿
保留旧快照
后台重试
好友状态不被错误改成离线
```

## 场景 7：完成比赛

好友完成一组题。

预期：

```text
生成一条动态
动态包含题数、正确率、用时、Rating、ELO 变化
最近比赛出现该比赛
报告生成后可以点击打开
```

## 场景 8：报告缺失

比赛存在但报告尚未同步。

预期：

```text
比赛仍然显示
报告按钮显示暂不可用
不能导致整个好友页崩溃
```

## 场景 9：版本号

检查：

```text
左下角
设置页
更新弹窗
Tauri get_app_version
```

预期全部一致。

# 十七、遇到不确定情况时的处理原则

如果实现过程中发现多个方案，按以下优先级选择：

1. 数据不丢失；
2. 不误添加陌生好友；
3. 不误判在线状态；
4. 不上传隐私；
5. 不阻塞刷题；
6. 不破坏 v1.4.3 现有功能；
7. 不大改 UI；
8. 最后才考虑自动化和便利性。

以下情况不得擅自扩大范围：

- 重写整个好友同步服务；
- 更换坚果云；
- 引入新的云服务；
- 新增登录系统；
- 新增后端服务器；
- 修改数据库核心表；
- 修改评分和 ELO；
- 重构整个 InsightsView；
- 增加新的主导航入口。

如果当前实现无法严格满足“实时”，必须在 UI 中诚实显示为：

```text
近实时
```

不能通过修改文字把轮询伪装成实时推送。
